# 武将列表（城堡家臣名单）构建链 — 新生儿为何不出现

静态分析对象：`clean_dump.bin`（VA = 文件偏移 + 0x400000，即**原始**字节；big.exe 池基常量被 P1 重定位到 0x53C000，但 47B 步长、字段偏移、下列例程地址/指令均不变）。
辅助：`lp.py`（capstone 反汇编 + 全镜像 E8/E9/立即数 xref），复用 `_172_buckets.txt`/`CHILD_STATE_RECIPE.md`/`child_stub.py`/`child_growth.py`。

## 0. 结论速览

每城 `武将列表` 由例程 **`0x4193B0`** 生成，它**不扫描池槽、也不看 `ent+0x24`（国|城）**，而是**遍历该城的“家臣链表”**：表头 = `[0x51eb88 + 城*31 + 0]`，节点 next = `[ent+4]`。一个人要进名单，**必须被挂进这条链表**。链表挂载的唯一原语是 **`0x4A0540(list_head, ent, 1)`（头插/尾插，已在链上则幂等）**，而它只被 **挂载/元服例程 `0x4A5100` / `0x4A5290`** 调用（调用点 `0x4A517D` / `0x4A56B8`）。
新生儿走的是我方 `child_pass → make_child → place_child`（`child_stub.py`），**`place_child` 只把父亲的 `word[ent+0x24]` 抄给孩子，从不调用 `0x4A0540`**，孩子因此**根本不在该城链表上 → 不被遍历 → 不显示**。即便补挂，`0x4193B0` 的过滤器 `test byte[ent+0x2c],0x90` 也会因孩子被 recipe 故意置起的 **bit4（0x10，排除位）** 直接跳过它。⇒ 这是**原生/预期行为**（元服前不进店/家臣名单），非“某个字段没填”那么简单——见 §4。

## Q1. 名单构建例程与迭代边界

调用链：`0x41A7CE` → `0x4191B0`（窗口过程；`jmp 0x419560`）→ `call 0x4191C0` → `call 0x4193B0`。
`0x4193B0` 头部：确定“主角所在城”并取该城链表表头：

```
004193B5  6a11              push 0x11
004193B7  e874640800        call 0x49f830          ; eax = 主角实体（0x49f830 用 [eax*2+0x50bf18] 把“行动者17”映射到 oid 再匹配 ent+2）
004193BC  8a4025            mov  al, byte ptr [eax+0x25]   ; 城 = ent+0x25（word+0x24 的高字节）
004193C2  3cc8              cmp  al, 0xc8
004193D3  8bf0              mov  esi, eax
004193D5  c1e605            shl  esi, 5            ; *32
004193D8  2bf0              sub  esi, eax          ; *31
004193DA  81c688eb5100      add  esi, 0x51eb88     ; esi = 城记录 = 0x51eb88 + 城*31
004193F8  8b36              mov  esi, dword ptr [esi]   ; ★ 取该城家臣链表【表头指针】
004193FA  33ed              xor  ebp, ebp          ; 输出数组下标
004193FC  85f6              test esi, esi
004193FE  744d              je   0x41944d          ; 空链表 → 直接结束
```

遍历体（每个节点）：

```
00419400  bf00800000        mov  edi, 0x8000        ; bit15 掩码
00419405  8bce              mov  ecx, esi           ; ecx = 当前实体（链表节点）
00419407  e8f4140800        call 0x49a900
0041940C  85c0              test eax, eax
0041940E  7536              jne  0x419446           ; 过滤1：身分码==7(大名) 跳过
00419410  f6462e01          test byte ptr [esi+0x2e], 1
00419414  7530              jne  0x419446           ; 过滤2：ent+0x2e bit0(事件占用) 跳过
00419416  f6462c90          test byte ptr [esi+0x2c], 0x90
0041941A  752a              jne  0x419446           ; 过滤3：bit7|bit4 跳过  ★孩子在此被拒
0041941C  56                push esi
0041941D  e8be200a00        call 0x4bb4e0
00419422  83c404            add  esp, 4
00419425  85c0              test eax, eax
00419427  741d              je   0x419446           ; 过滤4：见 0x4bb4e0（+0x12/+0x13）
00419429  f6462e04          test byte ptr [esi+0x2e], 4
0041942D  7517              jne  0x419446           ; 过滤5：ent+0x2e bit4 跳过
0041942F  66857e2c          test word ptr [esi+0x2c], di
00419433  7511              jne  0x419446           ; 过滤6：bit15(不在场) 跳过
00419435  8b0dc0e95100      mov  ecx, dword ptr [0x51e9c0]
0041943B  8bc5              mov  eax, ebp
00419442  45                inc  ebp
00419443  893481            mov  dword ptr [ecx+eax*4], esi   ; ★ 通过者压入输出数组 @0x51e9c0
00419446  8b7604            mov  esi, dword ptr [esi+4]        ; ★ next = ent+4
00419449  85f6              test esi, esi
0041944B  75b8              jne  0x419405
```

**迭代边界 = 指针链，无槽上界**：循环条件是 `esi = [ent+4]` 直到 NULL，**没有 `cmp …,0x172/CAP`，也不遍历 0..CAP**。这正好解释“扩展槽(371..462)的人照样进名单”——只要他被挂上过链表，槽号无关。行渲染段（`0x41944D..`）把入选实体指针 `sub esi,0x519868` 后用魔数 `0xae4c415d`（÷47）算出**槽号**，`call 0x4a0ff0` 写进列表框对象（`0x4a1110` 建、`0x4a0ff0` 填行）；名字最终按**槽**查姓/名表（INST `0x47F7B0` 已写）。

## Q2. 选择器会不会因“低 nibble / 元服 / bit” 拒掉孩子

- 名单构建器 **不测试 `[ent+0x2c] & 0xf`（低 nibble）**，也**不测年龄/元服**。孩子 nibble=0x0B **不是**被这个窗口拒的原因（nibble=0xb 只被**我方** `培养孩子` 面板与原生 `0x49A610` 事件派发用来识别“待期儿童”）。
- **真正卡住孩子的位**：过滤器3 `test byte ptr [esi+0x2c], 0x90 / jne 0x419446`（`0x90 = bit7 | bit4`）。孩子由 `CHILD_STATE_RECIPE.md §S2.3` 经 `0x49A6D0(1)` **故意置起 bit4=1（排除位）**，故命中 `jne`→跳过。
- 过滤器1 `0x49A900`：`mov ax,[ecx+0x2c]; and eax,0x700; cmp eax,0x700; sete` — 只把**身分码 bits8..10==7（大名）**者排除；孩子身分码=0，此关**通过**。
- 过滤器6 `test word[ent+0x2c],0x8000`：要求 **bit15=0（在场）**。孩子 `0x49A860(0)` 已清 bit15，此关**通过**。
- 同族证据（家臣解析访问器 `0x408DC0`，唯一调用点 `0x408DAE`）：
  ```
  00408DE2  f6402c10   test byte ptr [eax+0x2c], 0x10   ; bit4
  00408DE6  7403       je   0x408deb
  00408DE8  33c0       xor  eax, eax                    ; bit4=1 ⇒ 返回 NULL
  ```
  ⇒ 只要 bit4=1，家臣解析也拿不到该实体，孩子被系统性地当成“非家臣”。

## Q3. 名单“键”在于什么，逐行读了哪些字段

**键 = 城家臣链表成员资格**（表头 `0x51eb88+城*31`，链 `[ent+4]`）。链表由 `0x4A0540` 维护：

```
004A0540  ...  头插：mov edx[+4],ecx / mov [esi],edx   (arg3==1 走此路)
          尾插：走到链尾后 mov [last+4],edx ; mov [edx+4],0
          已在链上 → 直接 ret（幂等）
```
`0x4A0540` 的全部调用点里，与本问题相关的是 `0x4A517D`（在**挂载原语 `0x4A5100`** 内）和 `0x4A56B8`（在 `0x4A5290` 内）；两者都是**元服/归属**路径（`child_growth.py:25-30` 明述 `0x4A5100`：先校验主人→写本人国/城→`0x4A0540` 进链→`+0x16=0,+0x12=0xff,+0x13=城-0x38`→身分码 0→1；**不写主君 +0x2a**）。

每个显示行/过滤读取的字段（除链表指针外）：
| 读取处 | 字段 | 用途 |
|---|---|---|
| `0x4193BC` | 主角 `[+0x25]` | 选哪座城（用主角的城，**不是**被显示者的 +0x24） |
| `0x49A900` | `[ent+0x2c] & 0x700` | 身分码==7 大名 → 排除 |
| `0x419410` | `[ent+0x2e] & 1` | 事件占用瞬态位 → 排除 |
| `0x419416` | `[ent+0x2c] & 0x90` | bit7/bit4 → 排除 ★孩子命中 bit4 |
| `0x4BB4E0` | `[ent+0x12]==0xff` 且 `[ent+0x13]==[ent+0x25]` | “确属此城”门（值由 `0x4A5100` 挂载时写） |
| `0x419429` | `[ent+0x2e] & 4` | 瞬态位 → 排除 |
| `0x41942F` | `[ent+0x2c] & 0x8000` | bit15 不在场 → 排除 |
| `0x419483` | `ent - 0x519868` ÷47 → 槽号 | 行标识（名字再按槽查姓/名表） |

**没有读**：`ent+0x24`（国|城，用于**选城**的是主角那份而非个体）、`主君 +0x2a`、登场标志 `0x519288[oid]`、池槽区间。⇒ 名单**不靠** `+0x24` 匹配、**不靠**主君、**不靠**登场表；这些即便我方给孩子设了也不足以进名单。

## Q4. 定论：原生行为，还是我方漏设字段？

**是原生的“未元服即不入家臣名单”行为，同时叠加了我方的有意排除。** 拆解：

1. 新生儿缺席的首要且充分原因是**“未被挂进城家臣链表”**。原生体系里，一个人进入某城名单的唯一途径是挂载 `0x4A0540`，而这一步发生在**元服**（`0x4A5100`/`0x4A5290`，由 `0x4A4FC0` 按身分码派发）。所以 **BSDATA 原生儿童在元服前同样不会出现在该城 `武将列表`**——这是引擎设计，不是 bug。
2. 我方 MOD 恰恰**复刻并强化了**这一排除：`CHILD_STATE_RECIPE.md §S2.3` 明确把 `bit4=1`（`0x49A6D0(1)`）当作“让孩子不进 AI/家臣名单、从而不被招募/死亡/退隐机制吞掉”的保险，验收项⑤要求“AI 名单里没有他”。`make_child` 置 bit4=1、`place_child` 只搬 `+0x24`，**二者都不调用 `0x4A0540`、不设 `+0x12=0xff/+0x13=城`**。⇒ 孩子既不在链上、又带排除位，双重落榜，且这是**符合配方意图**的。

**若产品需求是“新生儿也要立刻出现在本城 `武将列表`”**，则需要补的是**链表成员 + 三处被门读的字段**（不是再动 `+0x24`）：
- 调 `0x4A0540(city_record, child_ent, 1)` 把节点挂进 `0x51eb88+城*31` 的链表（城记录=`0x51eb88+城*31`，节点=`ent`，next=`ent+4`）；
- 清排除位 `0x49A6D0(0)`（`[ent+0x2c] bit4 := 0`）以过 `0x419416`；
- 设“确属此城”门：`[ent+0x12]=0xff`、`[ent+0x13]=城`（与 `[ent+0x25]` 一致）以过 `0x4BB4E0`。
（保留 bit15=0、身分码≠7。）
代价：这会**同时关掉配方 §1 的“免疫死亡抽签/bit4 随机解禁/不被 AI 招募”保护**——因为那套保护正是靠 bit4=1 + 不在链上实现的。更贴近原生的做法是**维持现状**（孩子元服后由 `0x4A5100/0x4A5290` 自然入名单），而不是把婴儿直接塞进家臣链表。
