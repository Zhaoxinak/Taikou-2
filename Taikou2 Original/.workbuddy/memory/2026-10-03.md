### 结论：脱壳已完成，无需再破

## 追加：HD.exe 按钮失效的原因 + 纯净脱壳版产出

### HD.exe 不是纯脱壳，是"高清分辨率破解补丁"（已证实）
用户反馈"进界面后按钮点不动"。实测：
- `TAIK2W95_clean.exe` 主窗口 **646×449**（原 640×480）
- `TAIK2W95_HD.exe`   主窗口 **1606×1049**（被改到 1600×1000）
→ 画面放大了 2.5 倍，但按钮命中判定仍按 640×480，鼠标坐标对不上。

HD 版相对纯净镜像的改动（共 .text 24 字节 + .data 546 字节，其中 496 字节是 IAT）：
| 位置(RVA) | 原始 | HD 改动 |
|---|---|---|
| 0xEB9BD (.data) | `cmp eax,0x280;jl` + `cmp [esp+C],0x190;jle` | 25 字节 NOP（删除 640×480 校验）|
| 0xF1FFF (.data) | `mov ecx,[ecx*4+0x528958]` / `mov eax,[eax*4+0x529218]` | 写死 `mov ecx,0x640` / `mov eax,0x3E8`（1600×1000）|
| 0xF1F55 / 0xEFB8F / 0xEBA80 (.data) | 正常流程 | 改成 `jmp +0x4xxxx` |
| 0x6E950 / 0x6EA60 / 0x98F30 (.text) | 函数体 | `mov eax,1; ret`（强制返回真）|
| 0x6E9AC (.text) | `call ebx;test eax,eax;jne` | `jne` 被 NOP |
| 0x6EC00 (.text) | `call..;test ax,ax;jge` | `mov al,0x2E; ret` |

### 关键地址（后续 mod 直接可用）
- **真实 OEP = 0xF44B0**，落在 **.data** 内（不是 .text！）。是标准 VC5 CRT 入口：
  `55 8b ec 6a ff 68 58 cf 4f 00 68 b8 4d 4f 00 64 a1 00000000 50 64 89 25 ...`
- UPX 存根：RVA **0x1311A0 ~ 0x131347**，最后一条 `E9 68 31 FC FF` = jmp OEP（file 0x6D743）
- UPX 导入 blob 解压后位于 **RVA 0x130000**；DLL 名 RVA = `name_off + 0x1329C4`，
  IAT RVA = `iat_off + 0x1000`；每项函数名格式 `01 <name> 00`，`00` 结束本 DLL
- IAT 实际位于 **0xFB000~0xFB1F0**（.data 内，共 121 槽）：
  GDI32@0xFB000(26) KERNEL32@0xFB06C(55) USER32@0xFB14C(38) WINMM@0xFB1E8(2)
- 区段映射坑：加壳版 section2(UPX1) file = RVA - 0xC3C00；.rsrc file = RVA - 0xC4800

### 脱壳方法（无需实现 NRV 解压、无需 32 位 Python）
把存根最后的 `jmp OEP` 改成 `EB FE`（死循环）→ CreateProcess 启动 → sleep →
ReadProcessMemory 读 0x400000 起 0x133000 字节 → 得到完整干净映像。
再用 blob 重建正规 PE 导入表（IAT 槽写 hint/name RVA，交给加载器填充）。

### 产物
- `TAIK2W95_clean.exe` — 纯净脱壳版，无补丁，冒烟测试通过
- `.rev/dump_oep.py` 存根 dump、`.rev/parse_imports.py` 解析导入、
  `.rev/build_clean.py` 重建 PE、`.rev/show_patches.py` 对照补丁、`.rev/smoke.py` 冒烟测试
- `.rev/clean_dump.bin` 干净内存镜像（后续分析基准）

## 追加：大地图崩溃根因 = 原版 MP3.DLL 的 DirectShow 路径

### 根因链
BGM 播放 → `mciSendCommandA` → `mciqtz32` → `quartz`(DirectShow) → `devenum`
枚举解码器 filter → 加载系统 `msmpeg2ac3dec.dll` → 该 DLL 在 WOW64 下
以 **0xC0000602 (STATUS_FAIL_FAST)** 主动自杀 → 整个进程被杀。
- 动画走的是 **VfW**（`mciavi32` + `iccvid`），安全，与崩溃无关
- 原版加壳 exe 同样崩（7.9s，同码）→ 与脱壳无关，是游戏本身在现代系统的问题

### 关键调用点
- `RVA 0x12D342`: `ff 55 20` = `call [ebp+0x20]` → `mp3play(const char* path)`，**stdcall**
  （调用后无 `add esp,4`，被调用者 `ret 4`）
- `RVA 0x12D3A8`: `ff 55 28` → `mp3stop()`，无参数
- `mp3seek` 在 exe 中从未被调用（`ff 55 24` 出现 0 次）
- 路径格式：`.\MP3\NN.MP3`（NN 为两位编号，共 34 首）

### 解决方案：自写 mp3.dll（本机无 C 编译器，手工拼装 PE + x86 机器码）
`.rev/make_mp3dll.py` 生成 2048 字节的 32 位 DLL：
- 导出 `mp3play` / `mp3seek` / `mp3stop`，基址 0x0F000000
- `mp3play` 把路径末尾扩展名 `.MP3` → `.WAV`，交给 **WINMM!PlaySoundA**
  （flags `0x20009` = SND_FILENAME|SND_ASYNC|SND_LOOP），完全绕开 DirectShow
- 需先用 ffmpeg 把 `MP3/*.mp3` 转成 `MP3/*.wav`（pcm_s16le 44.1k 立体声，共 34 首 ~447MB）

### 踩过的坑（重要）
1. **PlaySoundA 参数压栈顺序写反** → 导致"函数被调用、路径也拼对，但没声音"。
   stdcall 从右往左压：`PlaySoundA(pszSound, hmod, fdwSound)` 必须
   `push fdwSound; push hmod; push pszSound`。写成正序会让 pszSound=0（等同停止播放）。
2. `C7 05 <abs32> <imm32>` 中 imm 在 `abs 起点 +4`（不是 +6），重定位项只需覆盖 abs32。
3. `A3 <abs32>` / `68 <imm32>` / `BF <imm32>` 的 imm 在 opcode 后 **+1**；
   `FF 15 <abs32>` / `FF 05 <abs32>` 在 **+2**。
4. 读 32 位被调试进程必须用 `Wow64GetThreadContext`（不是 `GetThreadContext`）；
   `WOW64_CONTEXT` 只有 Dr0–Dr3、Dr6–Dr7，按 x86 CONTEXT 写 8 个会整体错位 8 字节。
5. 调试器里对**非**自己下的断点异常必须用 `DBG_CONTINUE(0x00010002)` 交还程序 SEH，
   否则等于替程序吞异常，进程会卡在 EIP=0 反复触发。
6. `0x4000001F` 是 WOW64 伪断点（STATUS_WX86_BREAKPOINT），不能判为致命异常。

### 诊断技巧
在自写 DLL 的 .data 尾部放计数器（调用次数 / PlaySoundA返回值 / flags / pszSound），
用 `.rev/bgm_verify.py` 直接 ReadProcessMemory 读取 —— 零断点、不干扰游戏，
比在调试器里下断点可靠得多（调试器会严重拖慢游戏，推进不动）。

### 产物
- `TAIK2W95_bgm.exe` — **最终版**（clean 代码 + 恢复动画与 BGM），`StartTaikou2.bat` 已指向它
- `mp3.dll` — 替代品（原版备份为 `mp3.dll.orig.bak`）
- `MP3/*.wav` — 34 首转码后的 BGM
- 中间测试版（fix/nomp3/musA/mod）已归档到 `.rev/variants/`

## 追加：大窗口补丁（TAIK2W95_wide.exe）

### 游戏的多分辨率机制（逆向确认）
- 原生逻辑分辨率 **640×400**（不是 480；窗口 646×449 = 640×400 + 边框）
- 分辨率数组（运行时填充）：宽 `[0x528958+idx*4]`、高 `[0x529218+idx*4]`、
  当前档 `[0x52C5A8]`、hwnd 数组 `[0x52B5B8+idx*4]`
- 全链路：`0xEBA80` push 高400/宽640 → `call 0xEFAC4`（注册 hwnd、idx=[0x52B760]++、
  数组槽先 or -1）→ `call 0xF214C`（写数组 0xF22FB/0xF2303、MoveWindow 调窗口）
- 鼠标唯一入口 `0xF1FCB`：GetCursorPos → ScreenToClient → clamp 到数组值-1
- 游戏 UI 按"当前分辨率"自适应布局：背景瓦片平铺、场景居中、对话框贴角

### HD 版按钮点不动的真正原因
HD 在鼠标入口加了 `x*640/屏宽, y*400/屏高` 的换算 —— 但游戏 UI 本来就按
大分辨率布局（画布坐标 = 客户区坐标），换算把坐标缩小 2.5 倍导致全部错位。
**正确做法：不改坐标，只改分辨率来源，数组自动跟上，坐标系天然一致。**

### 补丁（clean.exe → wide.exe，仅 10 字节）
| RVA | 原 | 新 | 说明 |
|---|---|---|---|
| 0xEBA80 | 68 90 01 00 00 (push 400) | 68 20 03 00 00 (push 800) | 高 ×2 |
| 0xEBA85 | 68 80 02 00 00 (push 640) | 68 40 06 00 00 (push 1600) | 宽 ×2.5 |

0xEB9BD 的 `cmp eax,0x280 / cmp [esp+C],0x190` 是**桌面分辨率下限校验**（≥640×400），
现代屏幕轻松通过，无需动。另 3 处 push 640/400（0x76C5/0xEAE30/0xEAEB3）HD 未改也能
铺满，说明后台缓冲跟随数组，无需动。

### 验证
- 截图（.rev/snap_*.png + .rev/snap.py）：窗口 1600×800，UI 自适应布局正确
- 运行时数组（.rev/check_res.py）：wide=[1600,800]、clean=[640,400] ✓
- 音乐：wide.exe 自动加载替代 mp3.dll，PlaySoundA 返回 1 ✓
- `StartTaikou2.bat` 已指向 TAIK2W95_wide.exe（= clean 代码 + 分辨率补丁 + mp3.dll 音乐）
- 注：spy.py 调试器下游戏常以 255 自行退出（零异常），为调试环境现象，真实双击不受影响

### mod 用途的关键地址备忘
- 分辨率：宽数组 0x128958 / 高数组 0x129218 / idx 0x12C5A8 / 逻辑宽高 0x126CF0、0x129958
- 想改其他档位：改 0xEBA80 两个 push 立即数即可（push 高; push 宽，注意压栈顺序）

## 追加：内容真 2x 放大 (TAIK2W95_zoom.exe, 调试中)

用户反馈 wide.exe"窗口大了但游戏画面还是小"——游戏 UI 按分辨率数组自适应布局,
但地图视口/面板/字体按固定像素画,数组变大 ≠ 内容变大。

### 方案(与 wide 本质不同)
画布(8bpp DIB)+分辨率数组保持 640×400,窗口客户区 1280×800,
present 处把 1:1 BitBlt 换成 StretchBlt 整幅 2x 拉伸,鼠标坐标 ÷2。

### 关键发现
- present 函数: RVA 0xEFA94 处 push 参数+call 0xF28E5(BitBlt wrapper),
  尾部 ReleaseDC + pop edi/esi/ebx; leave; ret
- 窗口尺寸收敛循环: 0xF214C 内 SetWindowPos→GetClientRect→比对
  [0x526CF0](逻辑宽,来自 w 参数)/[0x529958](逻辑高,来自 h 参数)→调整→循环,
  **收敛目标由参数决定,改首次 SetWindowPos 会被循环拉回**。
  正确做法: 0xF220C `mov eax,[0x526CF0]`→`mov eax,1280`、
  0xF2211 `mov ecx,[0x529958]`→`mov ecx,800`(常量,同长替换)
- 鼠标唯一路径 0xF1FC7: GetCursorPos→ScreenToClient→0xF1FF6 写出+clamp,
  30 字节整块挪进洞补 ÷2(必须保持 eax=outx 指针/edx=outy 指针的寄存器契约!)
- 代码洞放扩容的 .idata(RVA 0x134000,VA **0x534000**; 曾误写 0x434000=VA/RVA 混淆)
- StretchBlt 不在导入表 → cave 里 LoadLibraryA("GDI32.dll")+GetProcAddress 惰性解析
- **jmp 而非 call 进洞**: call 会压返回地址,洞尾 ret 会弹回 NOP 雪橇

### 踩坑记录
1. VA=RVA+0x400000,别再把 0x134000 当 VA(应为 0x534000)
2. 补丁点对齐必须用字节搜索验证,hex dump 肉眼对齐错 1-3 字节两次
3. 替换函数尾段时,用 jmp 保持栈平衡; call 需要洞内 ret 前弹掉压入的返回地址
4. 动画播放期间主循环阻塞等 MCI(OPENNING.AVI 232s),present 只跑 2 帧,
   主窗口黑屏是常态——验证画面必须等动画结束或跳过

## 追加：zoom.exe 黑屏根因与最终修复（已通过验证）

### 黑屏真凶（极具迷惑性）
StretchBlt **返回 1（成功）**、g_pSB 解析正确、RECT=(0,0,1280,800) 全都正常，
但窗口全黑。原因：洞里 `push [0x534008]/[0x53400C]` 取目标宽高，而这两个地址
**从未被写过**（零页恒 0）；GetClientRect 的 RECT 写在 **0x534010**，
right=**0x534018**、bottom=**0x53401C**。
→ 实际执行 `StretchBlt(hdc,0,0,0,0,...)`：宽高 0 时 GDI 什么都不画却返回 TRUE。
**教训：GDI 返回 TRUE 不等于画了东西；宽高为 0 是静默失败。**

### 最终补丁表（clean.exe → zoom.exe）
| RVA | 原 | 新 | 作用 |
|---|---|---|---|
| 0xF220C | `a1 f0 6c 52 00`(mov eax,[0x526CF0]) | `b8 00 05 00 00`(mov eax,1280) | 窗口收敛目标宽 |
| 0xF2211 | `8b 0d 58 99 52 00`(mov ecx,[0x529958]) | `b9 20 03 00 00 90`(mov ecx,800) | 窗口收敛目标高 |
| 0xEFA94 | 48 字节 BitBlt+ReleaseDC+收尾 | `e9` 跳拉伸洞 + NOP×43 | present 改 2x |
| 0xF1FF6 | 30 字节鼠标写出 | `e8` 调坐标洞 + NOP×25 | 鼠标 ÷2 |

洞页 VA 0x534000：+0x00 g_pSB、+0x10 RECT、+0x20 "StretchBlt"、+0x30 "GDI32.dll"、
+0x40 present 计数、+0x44 StretchBlt 返回值、+0x80 拉伸代码、+0x180 坐标代码。
`StretchBlt(edi,0,0,RECT.right,RECT.bottom,[esi+0x529080],0,0,[esi+0x528958],[esi+0x529218],SRCCOPY)`
（edi=GetDC 到的窗口 DC，[esi+0x529080]=画布 DC）

## 追加：MOD 可行性评估（产出 `.rev/MOD_FEASIBILITY.md`）

用户问"这个游戏可以做 mod 吗"。三层结论：

### L1 代码层 = 已打通（工具齐全）
zoom.exe = clean.exe + 4 处补丁 + 扩容 `.idata`（+9216B），入口同为 RVA 0xF44B0。
改常量 / 改分支 / 注入 API（洞内 LoadLibraryA+GetProcAddress）/ 运行时探针 全部已验证。

### L2 数据层 = 可写但结构体未破
- `SNDATA1.TR2` = `TAIKOU2_SCENARIO`(40856)、`BSDATA1.TR2`(41300)、`SAVEDATA.TR2`、
  `NPKDATA.IDX`(IDX+0x6017 项偏移表)、`GAIJI.TR2`(544)
- **全文件 GBK 扫描几乎无可读名字** → 名字走索引引用，数值在结构体里
- `GAIJI.TR2` 是纯点阵 544B，唯一能直接改的资源，适合当验收样本

### L3 资源层 = 只读，当前唯一硬门槛（LS11 未破）
- 容器：`LS11` + 12 字节零 + payload（offset 0x10 起）
- 二级容器：`MSGX`×5（文本）、`ANMX`×1（ANMSEQ）、`IDX`×2，其余是裸像素/地图
- **`.preview/decoded` 有 33 份产物但解码脚本没留存** → 能看不能再生产，更谈不上重打包
- 算法线索：payload 熵 **7.218 bits/byte**、前 1024B 覆盖全部 256 个值、无明文穿插
  → **排除朴素 LZSS/LZ77**，更像 Huffman/算术/带密钥混淆
- **`clean_dump.bin` 搜 ASCII `LS11` = 0 命中** → magic 不是靠常量比较识别的
- 陷阱：`FACE.LZW` 1MB→1621B、`SHOPCHAR.LZW` 478KB→27KB，产物只是**单条子项**
  不是完整解压流，不能当解压结果用

### 破法建议

### 容器规格（实测）
- `0x000 LS11` / `0x010` 256B 字典（**256 元双射**，反查唯一）
- `0x110` span(段0) / `0x114` dec_len(段0) / `0x118` data_offset / `0x11c` span(段1)
- `0x120` 起 TOC，每条 12B = `[dec_len, start_offset, span(下一段)]`
  **段总数 = 1 + TOC 记录数**
- **每段独立 pad 到整字节**（pad 恒为 0/2/4/6 bit），各段可独立重压缩
- 早期误判"整文件一条连续 bit 流"→ 幸存者偏差，A/B 比对证明**必须按 TOC 偏移字节对齐**

### 压缩算法
- 索引编码 = **Elias gamma(n+2)**：`(K-1) 个 1 + 一个 0 + K 位载荷`，K=floor(log2(n+2))
- `idx<256` → 字面量 `dictionary[idx]`；`idx>=256` → `back=idx-256`，长度=下一 index+3
- 逐字节 `out[pos]=out[pos-back]`，允许重叠（标准 LZ77）
- **边界（全局实测极值）**：字面量 ≤255、**back ≤ 8191**(2^13-1)、**copy_len ≤ 512**
