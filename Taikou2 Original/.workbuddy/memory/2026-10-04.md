## 修复「家族族谱」一闪即被覆盖 → 变成数值错乱属性卡

### 症状
点卡片右上「家族族谱」页签 → 族谱树闪一下 → 画面立刻变成一张数值错乱的武将卡
（用户截图：大圣寺城/队长/71岁/统御力83 武力0 内政力215，全是垃圾数据）。

### 根因（反汇编 0x462D40 通用列表模态确认，两条独立缺陷）

| # | 位置 | 机制 |
|---|---|---|
| 1 | `0x47B590/0x47B430` | 触发族谱的那次左键**尚未释放**就进了列表模态；模态读实时键态，把"仍按着"当成"选中第 0 行"立即消费 → 族谱瞬间被关 |
| 2 | `0x462D98..0x462DA9` | 选中处理执行 `mov edx,[LISTBUF+sel*4]` / `mov [0x514EE8],edx` —— 把**当前查看武将(CARD_CUR)**换成被选中那行。族谱行的 LISTBUF 是洞内哨兵 `&FAM_ROWS[i]`，不是实体指针 → 信息卡拿洞内数据当武将属性渲染 |
| 3 | `0x462E03` 出口 | 族谱标志 `G_FAMILY` 在 ESC/选中退出时不清 → 残留后污染其它页；且模态期间的点击没被消费 → 主循环 ft_click 立刻重开族谱 |

**实机取证**：卡住时读 `[0x514EE8]=0x53571C`，正是构建日志里的 `FAM_ROWS` 地址 —— 铁证。

### 修复（build_fam_btn2.py v5，三个洞内 thunk）

| 补丁点 | 原指令 | 洞内 thunk | 作用 |
|---|---|---|---|
| `0x462D4C` | `test si,si; jne` | `0x535D60` fix_wait | 忙等左键释放（上限 0x400000 次，GetAsyncKeyState 经 RESOLVE_VA 惰性解析），再走原逻辑；si==0 分支也清 G_FAMILY |
| `0x462D93` | `mov edi,0x7fb` | `0x535DC0` fix_selchk | `G_FAMILY!=0` → 不走"选中切换"，直接走函数退出（族谱是只读视图） |
| `0x462E03` | `pop edi;pop esi;add esp,0x14;ret` | `0x535DE0` fix_exit | 所有退出口统一：`G_LBSEEN=[G_LBDOWN]` + `G_LBPREV=1`（消费模态内点击）+ `G_FAMILY=0`，再补回原尾 |

## 家族树改版为「树形 GDI 自绘 UI」并修掉 5 个静默缺陷

### 二进制布局（新节 `.fdata` RVA 0x136000 → VA 0x536000，0x3000 B）
```
O_GDITAB 0x0000(26 API 槽) O_GDINAM 0x0080 O_GDIOFF 0x0340 O_GDIMOD 0x0380
O_RSTATE 0x03C0 (256B)      O_SCRATCH 0x04C0 (RECT+MSG+POINT)
```

## 破：家族族谱页签「从其他界面进入角色详情时点了没反应」（通用模态泵钩子）

### 症状
只有从主城/自宅那条路径进信息卡时页签才灵；从**武将一览 / 其他界面**进角色详情，
点「家族族谱」完全无反应（不崩、不报错、日志一行都不出）。

### 根因（关键结论，值得记住）
触发点原来只挂在**一个**模态等待循环的头部 `0x46E31F`。
游戏里「信息卡可见」的等待循环**不止一个**：

| 循环头 | 来自哪条路径 |
|---|---|
| `0x46E31F` | 主城/自宅 → 角色详情（原来唯一挂的） |
| `0x4989E3` | 武将一览式列表 → 角色详情 |
| `0x4BA0DD` | 另一条入口 |

证据链（扫 `clean_dump.bin`）：
- `CARD_CUR = 0x514EE8`（当前信息卡武将实体指针）在 **5 处**被写：`0x44D1FA / 0x462DAB / 0x46E39B / 0x4989AA / 0x4BA0CB`
- `test byte[0x514E0C],2`（卡片在屏）= 卡片可见标志，出现在 `0x46E43C / 0x4989F2 / 0x4BA0EC` 三处
- **真正的公共点**：`0x4EEFA0` 是那 3 个循环**共用的模态泵**，全程序 **66 处**调用；
  另一族事件队列查询 `0x4EE0D0` 有 **29 处**调用。
- 补充实测：卡片**空闲时根本不重绘**（静默 1.2s → 卡片绘制 0 次），
  所以「只挂卡片绘制尾部」也不够，必须挂到泵上。

### 修法
不再逐个循环头打补丁，改为**挂公共泵**：

1. 新增共享探针 `ft_probe`（`PROBE_VA=0x5385A4`，88B，`pushad/popad` 全寄存器保护）
   - `G_BUSY`(0x535F40) 重入锁
   - 先看左键闭锁计数 `G_LBDOWN/G_LBSEEN` 有没有变化，没有就再试 F9（`ft_kbd`）
   - 命中才 `test byte[0x514E0C],2` 确认卡片在屏，然后 `ft_click` → `tree_entry`
2. `univ_thunk`（0x5385FC，15B）挂 **`0x4EEFA0` 入口**：复刻原首 5 字节 `53 56 57 8B F1` → `jmp 0x4EEFA5`
   **这一条就是核心修复**，66 处调用全覆盖
3. `univ2_thunk`（0x53860B，17B）挂 **`0x4EE0D0` 入口**（7 字节原指令：`e9 rel32` + 2×`90`）
4. 保留 `ft_btn_draw` 末尾 → `ft_probe`（不依赖泵的兜底），以及旧 `0x46E31F` 钩子

### 验证
- `tree_verify.py` → PASS（15 blob / 5660B，数据自洽，无 SIMD、无越区跳转）
  - 新增 `CAVE_LO/HI=0x535000-0x536000` 与 `EXT_OK` 外部目标白名单（`0x4EEFA0/5`、`0x4EE0D0/7`、`0x4989F2`、`0x4BA0EC`）
- **决定性实机验证**：`--no-nav` 关掉旧 `0x46E31F` 钩子重新构建，只留通用探测，
  页签照样命中：`>>> 页签命中 @(847,258)` + `家族查表: E3(命中)` + 拖拽 `PAN=(429,-133)` + `STAGE=12` 干净关闭 + `alive=True`
- 正式版同样通过

### 踩坑
- `ft_probe` 里 `callabs(KBD_VA)` 会因 `KBD_VA` 尚未定义而 `NameError` → 先硬编码 `0x535200`，后面补 `assert (0x535200,0x535300)==(KBD_VA,CLICK_VA)`
- `ft_btn_draw` 长到 300B，把 `0x535D60` 的 thunk 踩了 → `THUNK_WAIT/SELCHK/EXIT` 整体后移到 `0x535F80/FB8/FD8`，边界断言改成对 cave 大小 `0x1000`
- 构建时 exe 被占用会另存成 `TAIK2W95_familyb.exe` → 构建前先 `taskkill`

### 教训（通用）
老游戏里做「在模态循环里插自定义输入」这类 MOD，
**不要挂某一个循环头**——先扫出所有写卡片指针/判可见标志的站点，
找它们**共用的底层泵**（调用点最多的那个），挂泵入口 = 一次覆盖全部路径。

## 修复：家族树节点消失 + 游戏崩溃

### 现象
用户打开柴田家族树后只看到标题"柴田氏"和一条水平线，节点框/姓名全没显示，随后游戏崩溃。

### 根因
`tree_render.py` 配偶连线代码中手滑把 `ld(a, RS['SUBJX'])` 写成了 `ld(a, RV + RS['SUBJX'])`。
`ld()` 内部会再加一次 `RV`，结果生成 `mov eax,[0xA6C860]`——指向无效高地址。
运行时一进入配偶分支读取本人坐标就访问违规，绘制中断/崩溃。

### 修复
- `tree_render.py`：`ld(a, RV + RS['SUBJX'])` → `ld(a, RS['SUBJX'])`。
- 重新运行 `build_fam_btn2.py` 生成 `TAIK2W95_family.exe`。

### 验证
- `tree_verify.py`：**PASS**，渲染机器码语法合法。
- 配偶分支反汇编确认：`mov eax, [0x5364A0]`（正确的 SUBJX），不再出现 `0xA6C860` 坏地址。
- 柴田布局：胜家(105,109) 与 阿市(175,109) 平级紧邻，配偶水平线从胜家右缘连到阿市左缘。

### ✅ 最终根因（修正：上一轮只修了 SUBJX，崩因仍在）
用户反馈"还是没显示+立即崩溃"。复看 `draw_edges` 两段 `MoveToEx`：
- **父折线**：`_p8(a, 0x00)` → push y/x/hdc（4 参数，`lppt=NULL` 合法）。
- **配偶连线**：直接 push y/x/hdc，**漏了 `_p8(a, 0x00)` 这个 `lppt=NULL`**。
  `MoveToEx(hdc,x,y,lppt)` 是 4 参数 stdcall，第 4 参拿到栈上野指针，非 NULL 时
  `MoveToEx` 往野地址写 8 字节 → 访问违规崩溃。这与"画到配偶节点就崩、父折线先画完"完全吻合。
- 修复：配偶连线 `MoveToEx` 前补 `_p8(a, 0x00)`。重建后反汇编确认两处 MOVETO 前都恰好 4 个 push。
- 教训：手写 x86 调 Win32 GDI 时，**`MoveToEx` 第 4 参数 `lppt` 必须显式压 `NULL`**；
  这类"漏参数→野指针"的 bug，用 stub 的 Unicorn 仿真无法复现（仿真里地址都映射过不会 AV），
  只能靠精确比对指令序列或人工核对 stdcall 参数个数来抓。
- 本次两个 bug（SUBJX 野地址 + 配偶 MoveToEx 漏 lppt）都需修，缺一不可。
- `tree_verify.py` 末次重建：**PASS**，`draw_edges` 572B→574B（新增 `6A 00` push 0）。

## 修复：配偶水平连线太长、横穿兄弟节点

### 现象
用户截图：胜家 ↔ 阿市 那条青色配偶线拉得极长，一路穿过「弟 胜政」所在区域。

### 根因（布局槽位顺序，不是渲染 bug）
`tree_data.py` 的 `layout()` 用**后序 DFS**给叶子按 `kids[]` 插入顺序发牌槽位。
原先 `SHIBATA_NODES` 顺序里 `阿市(#3)` 排在 `胜政(#4)` **之后**（因为先写了弟再写正室），
`kids[0]` 因此变成 `[胜久,胜家,胜政,阿市]` → 槽位 0/1/2/3，
即：胜久(slot0) 胜家(slot1) **胜政(slot2)** 阿市(slot3)。
配偶线从本人 slot1 右缘画到配偶 slot3 左缘，自然把中间 slot2 的胜政整段贯穿。

### 修复
- `tree_data.py` `SHIBATA_NODES`：把「正室 阿市」挪到「本人 胜家」正后方、`胜政` 之前，
  → `kids[0] = [胜久,胜家,阿市,胜政]`，槽位顺序变为 胜久0/胜家1/阿市2/胜政3。
- 配偶线端点本来就是 `本人右缘 ↔ 配偶左缘`，槽位一相邻就自然变短（COL_W=70 - AV_W=26 → 44px）。

### 验证
- `build_layouts()[0]`：胜家(105,109) 阿市(175,109) 胜政(245,109)，胜家↔阿市相邻；
  内容框 236×245 不变。
- `tree_verify.py`：**PASS**（56 节点，坐标/父索引/串偏移全合法）。
- `build_fam_btn2.py` 重建 → 因 `TAIK2W95_family.exe` 仍被游戏占用，产物写为
  `TAIK2W95_familyb.exe`（1280000B）；需关闭游戏后覆盖。

### 教训
`layout()` 的槽位顺序 = **节点在列表里的出现顺序**（DFS 后序），
不是"我写注释说它紧邻就真的紧邻"。凡是依赖相对位置的渲染（配偶连线等），
必须先用 `build_layouts()` 打印实际 cx 确认，别只看注释。

## 修复：配偶节点仍被父亲的亲子线连接

     中间用 `MoveToEx` 直接跳过去（不画线）。
