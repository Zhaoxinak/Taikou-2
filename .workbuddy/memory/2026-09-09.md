### 🔴 重要发现：spec 文档自身有误，勿盲信
`diplomacy_spec.json` 的 `rel_lookup` 同时给了两种写法，其中 **asm 改写是错的**：
- ❌ `0x51dc5f + (j + 48*i - i*(i-1)/2)` → 最大 1222，**溢出矩阵 1176**，且不能覆盖 0..1175。
- ✅ `tri_index = i*49 - i*(i+1)/2 + (j-i-1)`（即 spec 的 "equivalent" / `diplomacy2_ref.tri_index`）
  → 实测 0..1175 全覆盖唯一。
**教训：反向 spec 里的汇编转录注释要数值证伪后再落地**（已在自测里固化该证伪断言）。

### 其他语义要点
- 主从関係是**有向关系存于无向矩阵**：存储 2/3 在 i>j 时镜像 5-v；(5,3) 读「支配」⇔ (3,5) 读「从属」。

## NPC 名表导出 + 接线（闭合 council / event_sys 的「名表未导出」诚实缺口）

**产出**：`scripts/export_npc_names.py` → `data/npc_names.json`；`tools/_test_npc_names.gd` 16/16。

**原版结构**（`scripts/council_ref.py` 0x49c2b0 四段路由，stride 7，内联 `\0` 结尾 C 串）：
- id 1000..1999 → `0x5077B0 + (id-1000)*7`
- id 2000..2999 → 运行时指针 `dword[0x506c54]`（**无静态名表**）
- id 3000+ → `0x507978 + (id-3000)*7`
- 编码 **GBK/gb18030**（cp932 解为乱码，已排除）

**🔴 踩坑：名表后面紧接的是其它数据结构**（调色板/查找表/指针区），其字节在 gb18030 下**恰好能解码成零散汉字/符号**（MID 区 踗/浇B/R；HI 区 挢/䎬/吏/E/>H）。
初版只查「长度 ≤6 + 无 `\ufffd` + 无控制符」→ 导出 190/177 条，尾部全是伪名；且**「7B 内含 `0x00`」单条判据仍不够**（3400+ 区每条都是 1 字 + 补零，照样有终止符）。

**✅ 三层过滤（缺一不可）**：
1. **7B 单元须含 `0x00`** —— 7 字节记录里至少 1 个 0x00 才是真正的 C 串单元；全非零 = 溢出串/打包数据，直接跳过。
2. **`is_name`**：去空白后 1..6 字；禁控制符、**禁 PUA(U+E000~U+F8FF)**、`\ufffd`；**禁任何 Latin 字母**（原版名表纯 CJK/假名/全角，绝无拉丁字母，此条直接杀掉 `浇B`/`>H`/`R`）；**须含 ≥1 个** CJK 统一表意/扩展A/假名/全角字符（杀掉纯数字纯符号 `0014`/`2`/`*`）。
3. **孤立滤除**：候选须在 `[id-5, id+5]` 窗口内 **≥3 个有效邻居** —— 真名块密集，数据区仅零星伪名（孤立的 踗/挢/吏/E），孤立者丢弃。
   ⚠️ 窗口阈值别取太严（±2/阈值3 会误杀稀疏真名如 `介绍信` 3042，其 ±2 仅 2 个有效；±5/≥3 下该窗口有 4 个 → 保留）。

## 野外画面全黑（world_screen 渲染踩坑，commit d058ec0）

**症状**：木下藤吉郎/明智光秀开局入大地图 → 顶部 HUD「所在：野外」+ 底部「方向键/WASD 移动 · Enter 进入 三户 · Esc 回状态画面」正常，中间全黑什么都看不到。

**根因**：Godot CanvasItem **子节点默认绘制在父 _draw() 之上**。world_screen._ready() 把全屏 `ColorRect` 当 bg `add_child(bg)`，导致 `WorldScreen._draw()` 画的 200 城点 + 城名 + 红色主角圆/黄高亮弧**全部被 bg 盖住**。证据：底部提示「进入 三户」正确 → `_nearest_id` 经 `WorldMapRef.nearest` 求出（logic 正常），纯渲染问题。

**修**：`bg.show_behind_parent = true`（让 bg 绘在父 _draw 之下，一行）。
**其它屏为何无此坑**：castle_town/status_screen 的可见内容是 child Controls（panel/label/button）且在 dim ColorRect 之后 add_child，绘制顺序天然「dim 在下 / UI 在上」正确；只有当父 _draw() 自身就是主内容时才需 `show_behind_parent`。

**验证**：tools/_test_world.gd **pass=15 fail=0**；_test_all_compile **45 ok/0 fail**。
**已记录**：MEMORY.md「GDScript/无头坑」加此条（父 _draw 是主内容的屏，bg 子节点必须 `show_behind_parent = true`）。
