## 1. 文件读取原语（已确认）

引擎用统一的"对象 + 文件流"模型加载数据。关键函数：

| 地址 | 语义 |
|------|------|
| `0x47da10()` | **从文件读 1 字节**，返回值在 `al` |
| `0x47da50()` | **从文件读 1 字（2 字节 LE）**，返回值在 `ax` |
| `0x47d910(dest)` | 读 1 字节 → `*dest` （内部 `call 0x47da10`） |
| `0x47d930(dest)` | 读 1 字 → `*dest` （内部 `call 0x47da50`） |
| `0x47da80(al)` | **写回** 1 字节到对象缓冲 `[ecx+0x9a]`，并 `inc [ecx+0x8e]`（字节计数）、`add [ecx+0x92], al`（校验和） |
| `0x47dac0(ax)` | **写回** 1 字（先低字节后高字节，两次 `0x47da80`） |
| `0x4411b0(buf, size)` | 块读取原语（用于签名校验 16B、以及疑似独立资源流如 700B 块） |

**加载对象 (esi) 关键字段偏移**：
- `+0x8c` : 模式/开关字（`0x47d910/0x47d930` 据此决定走 `0x47da10/0x47da50` 还是别的分支）
- `+0x8e` : 已读字节计数器（`inc` 每字节，到 `0x2000` 触发 flush `0x47d9b0`）
- `+0x90` : 头部字段 1（来自文件 offset 16-17，u16）
- `+0x92` : 头部字段 2（来自文件 offset 18-19，u16）+ 读回时累积为**校验和**
- `+0x94` : 头部字段 3（u16，加载时经 `XOR(ah, al)` 校验 → 期望 `0x0c`）
- `+0x96` : dword 指针/偏移（加载末尾 `add ecx, 0x9ffa` 参与定位）
- `+0x9a` : 输出缓冲当前写指针

> 注：`0x47dae0`（首个 sub-loader）只是把全局配置字节 `0x5205f0..0x520604` 拷入对象，并非文件读取。

## 2. SNDATA 结构（已破解 — 结构层）

**文件**：`SNDATA1.TR2` / `SNDATA2.TR2`（两文件结构相同、数据不同；均 40856 字节，**不**像 BSDATA 互为副本；两场景记录区差异 ~96%）。

**布局（经反汇编 stride 确认，非统计猜测）**：
```
[0:16]    ASCII "TAIKOU2_SCENARIO"  (16 字节签名)
[16:]     833 条 × 49 字节 记录 (记录 i 在 offset 16 + i*49)
[40833:40856]  23 字节尾部 (场景1=全 0x0C, 场景2=全 0x0A, 均匀终止符)
          校验: 16 + 833*49 + 23 = 40856  ✅
```
- 记录 0 的 `[16:20]` = 4 字节头（每场景不同: SNDATA1=`4b b8 bb b7`, SNDATA2=`13 80 b4 be`），其后是 45 字节 `0x01/0x00` 旗帜/枚举阵列。
- 记录 1 起始 `@65` 为全 0（试探性/模板记录）。

**记录尺寸如何确认（关键教训）**：
- ⚠️ **不要用自相关定记录尺寸**！`_find_record_size.py` 在 `S=59` 给出尖锐假峰（score≈0.48，谐波 118/177/236），但那是由于本文件 `0x01/0x00` 低密度内容造成的**统计假阳性**。
- ✅ **真值来自反汇编**：`0x47d890`/`0x47d8d0` 记录访问器为 `lea edx,[ecx+eax+0x10]`（eax=idx×stride）+ `push 0x31`(=49)，即每条记录 **49 字节**、stride 49、起始偏移 16。
- ✅ 字节总数 `40856-16 = 40840 = 833×49 + 23`（尾），精确整除。
- ✅ 尾部 `[40833:40856]` 实测为 23 字节均匀值（0x0C / 0x0A），是经典的终止符尾。

**记录内容（实测解码）**：每条 49 字节 = 4B 头 + 45B 阵列，值以 `0x00/0x01` 为主（低位标志/枚举），**不是**明文 GBK 姓名（与 BSDATA 不同——BSDATA 前 13 字节是姓名）。
- 记录 0 `@16` = `4b b8 bb b7` 头 + 45 字节 `0x01/0x00` 位域（≈390 个布尔开关 → 事件/成就/状态旗帜块）。
- 记录 1 `@65` 全 0（模板/占位记录）。
- 记录 100+（如 `@4916`）出现文本状字节（`c4 53 f3 f3 32 30 …`、`0c 0c 0c` 填充）→ 疑似角色名/文本块。**结论：833 条记录并非同类型**，前段为旗帜/枚举、后段为文本，需按子块分别映射（见 Task #23）。

**记录访问器（反汇编确认，最硬证据）** `0x47d890(idx)`（thiscall, ecx=对象）：
```
mov eax, [esp+4]        ; idx
and eax, 0xffff
lea ecx, [eax+eax*2]    ; eax*3
shl ecx, 4              ; eax*48
lea edx, [ecx+eax+0x10] ; = idx*49 + 0x10
mov eax, [esi]          ; 文件基址
push edx; push eax
call [0x4fb0a8]         ; fseek(base, idx*49+0x10)
push 0x31               ; 49
push ecx(=对象)
call 0x4411b0           ; read(49)
```
→ 每条记录 **49 字节、stride 49、起始偏移 16**，引擎**按需 seek+read 单条**（非批量加载），与加载函数里的 833×49 结构完全吻合。`0x47d8d0` 是同族访问器（改用 `0x4411d0` bulk 读）。

**SNDATA 加载函数** `0x47f350`：
- `push 0x4fc240`(字符串 `TAIKOU2_SCENARIO`) + 块读 16B → `call 0x492850`(strcmp) 做签名比对。
- 读 2B→`[esi+0x90]`，2B→`[esi+0x94]`（含 `XOR(ah,al)==0x0c` 校验）。
- `push 0x2bc(=700)` + `push 0x519288` + `call 0x4411b0` → 读一个 **700 字节块**（疑似独立于顺序流的资源，如 700 角色存在/标志数组）。
- `call 0x47d960` 初始化 + 清零 `[esi+0x92]`。
- 顺序调用 **18 个 sub-loader**（`0x47dae0`→`0x47f210`）逐段读取记录区；另有第二组 18 个（`0x47dba0`→`0x47f2a0`）做第二遍解析/写回。

**Loader 分段读图（Unicorn 实跑，详见 `scripts/_emu_sndata_loader.py` → `scripts/_sndata_trace.json`）**：
- 文件读原语 `0x4411b0` 按 **0x2000 块**填对象缓冲；对象读原语 `0x47da10` 从缓冲逐字节取（两者经 `[esi+0x94]` 密钥 XOR，实测该密钥=0 → 未加密）。

- 18 个 sub-loader 各自消费的字节跨度（顺序、相对文件流）：

## 2b. 记录类型与内容（实测，2026-08-24 重写）

**关键纠正**：833 条记录**非同质**。按字节统计 + 跨场景 diff + 填充槽识别，实际为三类：

### 类型分布（SNDATA1）
| 类别 | 记录范围 | 条数 | 内容 |
|------|----------|------|------|
| 头部 | 0 | 1 | 4 字节场景 ID（`4b b8 bb b7` S1 / `13 80 b4 be` S2）+ 45 位标志位域 |
| 标志位域 | 1 – 22 | 22 | 纯 `0x00/0x01`（少数全 `0x01` 如 15–17、全 `0x00` 如 19–22 = 全置位/全清零标志数组）|
| 字符串表 | 23 – 830（含填充槽）| ~690 | 每条含多个 **KOEI 私有码页** GBK 状字符串，以 `0x0C`/`0xF3` 分隔 |
| 填充槽 | 24–27 / 602–665 / 759–804 / 831–832（及 807,808,813,824）| ~120 | 整条单值：`0xFF`(S1) / `0x0C`(S1) / `0xF3`(S1) / `0x0F`；S2 对应槽为 `0x0A` 等 → 未使用的字符串表空位 |

- **字符串表是主体**（~690 条记录，每条 49 字节内可含 3–6 个以 `0x0C`/`0xF3` 分隔的短字符串，全文件约 4477 个文本 run）。
- **填充槽的填充字节随场景变化**（S1=`0C`/S2=`0A`），说明它是“本场景空标记”，非固定 padding。

### 文本编码 = KOEI 私有码页（已确认非明文 GBK，但记录性质有重大修正）
- ⚠️ **2026-08-24 深夜修正**：记录 23–830 **不是纯文本字符串表，而是结构化二进制记录**（固定布局 structs）。强制 GBK 解码出"汉字"是假象——同一字符在固定偏移反复出现（`篌`/`驨`/`岓` 几乎每条都有），这不是真实文本模式。
- `0x0C`/`0xF3` 是**结构体字段分隔符**，不是文本分隔符。
- 聚合统计 HH/(HH+HL)≈65% 看似 GBK 双字节签名，**但这恰好是随机二进制数据的自然比率**（GBK trail 字节 ≥0x80 的概率约 65%），不证明是 GBK 文本。
- 严格 GBK 解码：4477 个文本 run 中 **37.8% 直接报错**（如 `c4 3d` 的 trail `0x3d`<0x40 非法）。
- 单字节变换穷举（XOR/ADD 各 0–255）最高仅 70.6%（XOR 83），且无清晰峰 → 排除"GBK + 固定变换"。
- **结论**：SNDATA 文本字段用 **EXE 内部计算的编码**（GBK 码 → 字形索引 → 字体位图），不是标准 GBK，也不是简单的单字节变换。解码需逆向 EXE 字体加载器的 GBK→字形映射逻辑（见 §7）。
- 备注：MESSAGE*.LZW / BSDATA 姓名仍是明文 GBK（已破解），仅 SNDATA 场景字符串走 EXE 内部码。

### 跨场景差异（SNDATA1 vs SNDATA2）
- 833 条中 **805 条字节级差异 >20** → 绝大多数为**场景状态**（非静态主数据）。
- 仅 14 条两场景完全相同；4 条差异 ≤4 字节；10 条差异 5–20。
- rec 0 头部 4 字节 + 个别标志位在两场景不同 → 头部=场景标识，差异位=场景相关状态标志。

### 记录访问器调用关系（重要）
- `0x47d890` / `0x47d8d0` 是 `idx*49+0x10` 取单条记录的访问器（§2 已反汇编确认）。
- 但**全镜像中无任何对 `0x47d890`/`0x47d8d0` 地址的直接/间接立即数引用**（0 次出现）→ 引擎通过**虚表/寄存器间接 call** 读记录。因此“按调用点反推字段语义”不可行，须依赖 KOEI 码解码 + 运行期数据对照。

## 3. IDX 图形容器（已破解 — GRPDATA / HGRP）

**文件**：`GRPDATA.LZW`、`HGRP.LZW`（先经 LS11 解压，见 `REPLICATION.md` LS11 章节）。

**容器头**：
```
[0:3]   ASCII "IDX"
[3]     u8  条目数  (GRPDATA=0x8b=139, HGRP=0x7e=126)
[4:]    u32 LE 偏移表 (条目数 个, 指向各条目起始; 单调递增, 遇 0 或非递增终止)
```

**每条目**：
```
[0:2]   u16 LE  type  (= 3 → 3bpp / 8 色索引)
[2:4]   u16 LE  width
[4:6]   u16 LE  height
[6:]    3bpp 索引像素, MSB-first, 每 3 bit = 调色板索引 0..7
        理论字节数 = ceil(w*h*3/8), 实测全部条目 avail≥need ✅
```

**验证**（`_verify_idx.py`，非图片方式）：
- 139/139 (GRPDATA) 与 126/126 (HGRP) 条目字节充足。
- 索引全局分布非均匀（索引 0 = 透明背景占多数，其余 1..7 各异），证明解出的是**真实形状而非噪声**。
- ASCII 预览（灰度盘 `GRAY8A`，索引0透明）显示清晰字形/图标轮廓（8×16、8×8 等）。
- 两容器前几条目字节级相同 → 可能共享同一精灵/字模前缀集。

**真实调色板**：尚未获得（3bpp 仅 8 色，真值需代码驱动发现，见 §4）。当前用 8 级灰度仅用于验证形状。

## 4. 调色板（值扫描法已证伪）

`_hunt_palette.py` 尝试"扫描连续 ≤0x3F 的长 run（48/192/768 字节分类）"**完全失败**：
- 解密二进制中存在 226407 个 ≥24B 的 ≤0x3F run，最长 840963B 全零（属 `.bss`）。
- 988172 个 768B 窗口满足 ≤0x3F。
- 结论：**在解密后的引擎/数据二进制中，靠字节值分布定位 VGA 调色板不可用**。调色板必须从代码路径追踪（例如找到 `SetPalette` / 写 DAC 的调用，或图形加载函数里填充 768B 缓冲的位置）。本任务降级完成，留待深度逆向。

## 7. 字体系统（2026-08-24 逆向进行中）

### 7.1 rmKOEI.bin = 卸载程序 DLL（不是字体渲染器）

**重大纠正**：旧文档/记忆记 rmKOEI.bin 为"位图字体渲染 DLL"，**实测为误**。

- PE DLL（24,576B），3 节：`.text`(vsize 0x2b46) / `.rdata`(0xa00) / `.data`(0x2600)。
- `.rdata` 含 MSVC 运行时错误字符串 + API 导入表：
  `MessageBoxA`(user32) / `DeleteFileA` / `RemoveDirectoryA` / `SetFileAttributesA` / `SetCurrentDirectoryA` / `GetWindowsDirectoryA` / `lstrlenA` / `lstrcpyA`(KERNEL32) / `SHChangeNotify`(SHELL32)
- **无任何字体/GDI API 导入**（无 `CreateDIBitmap`/`SelectObject`/`TextOut`）。
- `.data` 含明文 GBK 卸载程序字符串：`光荣卸载程序` / `指令行不正确` / `无法删除卸载程序` / `卸载完毕。` / `为了删除卸载程序使用的临时文件，请重新启动电脑。` / `无法移动到Windows文件夹。` / `检查Windows文件夹失败。`
- 源文件标记：`$Id: textsub.cpp 1.2 1996/01/17 02:44:02 Ashihara Exp Ashihara $`
- **结论**：rmKOEI.bin = KOEI **卸载程序 DLL**（textsub.cpp, 1996, Ashihara），与文字解码/字体渲染完全无关。

### 7.2 字体加载器（已定位在主 EXE 内）

脱壳后 EXE（`_unpacked_mem.bin`，基址 0x400000）内字体文件名字符串：

| 字符串 | VA |
|--------|----|
| `C:HBCHAR.LZW` | `0x5030e8` |
| `C:HBCHAR2.LZW` | `0x5030f8` |
| `C:HJCHAR.LZW` | `0x5034d0` |
| `C:HKCHAR.LZW` | `0x5034f0` |
| `C:TOWNCHAR.LZW` | `0x506bb0` |

**字体加载器函数 `0x424120`**（通过 xref `C:HBCHAR.LZW` 字符串定位）：
1. 读取 `C:HBCHAR.LZW` → 调用 `0x441330`/`0x441360`（LS11 解压）
2. `0x424320` 按字形索引 blit 位图到全局字形缓冲区：`stride = esi*5<<6` = 320 字节/字形
3. 字形缓冲区地址：`0x524a38` / `0x524918`

> 字形→字符的映射由**字体文件内字形的排列顺序**决定（加载器把字形 k blit 到 slot k），不是查表。

### 7.3 运行时字形表 0x519868

- 位于 EXE 数据段，**370 条目 × 47 字节（stride 0x2f）**。
- **加载时全为零**（`_unpacked_mem.bin` 中实测确认）——由字体加载器在运行时填充。
- 全镜像中 **588 处引用** `0x519868` → 中央运行时字形表，每次文本绘制都访问。
- `0x443810` 是字形缓存构建器：扫描此表，读 `byte[0x24]`（页选择器），检查 `0x2d`/`0x29` 标志位，计算 `shl ecx,3`(×8) 偏移。

### 7.4 字体文件字形统计

| 文件 | 解压大小 | 字形数 | 用途 |
|------|----------|--------|------|
| `HBCHAR.LZW` | 49152B | 1536 | 战斗精灵（16×16 1bpp EGA） |
| `TOWNCHAR.LZW` | 27136B | 848 | 城镇角色 |
| `HJCHAR.LZW` | 38464B | 1202 | 合战角色 |
| `HKCHAR.LZW` | 42560B | 1330 | 角色精灵 |

- 各字体文件字形集**不同**（非同一套字符子集），说明不同场景用不同字符集。
- 字体文件内**无内嵌字符码表**——纯位图数据。

### 7.5 无静态 glyph→GBK 查找表

- 扫描整个 `_unpacked_mem.bin`：最长连续"合法 GBK LE u16"run 仅 57 条（需 ≥200 才算表）→ **EXE 中无静态查找表**。
- "LS11" 魔术字符串在 EXE 中不存在（解压算法内联在代码中）。

### 7.6 GBK 处理签名聚集区 0x443xxx

- `cmp al,0x81`（GBK lead byte 检查）×14 次，如 `0x417b3c`/`0x44395b`/`0x443ab1`/`0x443c20`
- `cmp al,0xa1` ×6 次，如 `0x4023b5`/`0x444956`/`0x48a707`/`0x48e997`
- 聚集于 `0x443xxx` 段 → **真正的文本/字体模块**所在。
